Quorum Production Architecture
Quorum · target design · eu-south-1

Quorum in production

From one EC2 with files on disk to a managed AWS stack: Postgres as the single source of truth, S3 for files, the wiki kept in sync within seconds and in order, and answers tuned to who is asking. Everything is defined in CloudFormation; CloudFront comes later.

The system

Wiki → Quorum: async, but not eventual

The webhook returns in milliseconds and the work happens behind a queue, but each page change is applied exactly once, in the order the wiki made it, and Quorum can say for every page whether it is current. A change that goes missing is caught and repaired, never left to drift.

  1. Wiki fires a webhookpage created, updated, moved, deleted, attachment added.
  2. Lambda verifies and queueschecks the signature, writes {page, version} to SQS FIFO with the page as message group and page+version as dedup id. Returns 200.
  3. Worker fetches vNwebhooks are thin, so the worker reads the page body and restrictions from the wiki REST API.
  4. Embedchunks the page and gets vectors from the embeddings model through OpenRouter.
  5. One transactionpage row, chunks, vectors and permissions, applied only if vN is newer than what is stored. Readers see the old page or the new one, never half.
  6. Live sessions hear about it“The runbook you're discussing changed (v12 → v13)” in every session that uses the page.

What makes it reliable

  • Per-page order: FIFO message groups keep v13 behind v12; different pages run in parallel.
  • Idempotent: the version check makes replays and duplicates harmless.
  • Bounded lag: an alarm when the oldest message is older than 60 s; failures land in the DLQ, which also alarms.
  • Repair: every 15 minutes the worker compares the wiki's last-modified times with Postgres and re-queues anything behind.
  • Read your own writes: when Quorum writes back to the wiki, it stores the new version in the same request, so the echo webhook is a no-op.
  • Visible: a sync status per page (current, catching up, failed) in Admin.

Quorum → Wiki

  • Read API for the wiki: search, session reports, decisions, and document versions under /api/v1, behind API Gateway with throttling.
  • Machine identity: a Cognito app client with client-credentials and scopes like read:reports, used by a small Forge app or macro in the wiki.
  • Write-back: approved document changes go to the wiki with its version number, so a page edited in the meantime is a conflict to resolve, not an overwrite.

Answers that know who is asking

Each person has a profile: team, role, skills with a level (say Kubernetes 5, RF 2), areas they own, and how deep they like answers. People set it themselves; admins can adjust it; Quorum can suggest skills from activity, which the person confirms.

  1. Question + profilewho is asking, in which session.
  2. Permission filteronly chunks from pages this person may read in the wiki.
  3. Hybrid searchpgvector similarity plus Postgres full-text, in one query.
  4. Re-rank with skillsfavour sources in the person's areas; surface owners as people to ask.
  5. Prompt at their levelan expert gets the diff and commands; a newcomer gets context first.
  6. Answer with sourceslinks to the wiki pages and versions it used.

Decisions to make before building

  • Wiki permissions. Quorum must never answer from a page the person can't open in the wiki. Mirror page restrictions on sync and filter on every search.
  • PSIP and Quorum. Both index the same wiki. Decide whether Quorum reads from PSIP, or the wiki index moves into Quorum's Postgres. Two indexes of one wiki will disagree.
  • Write-back approval. Who approves a document change before it reaches the wiki, and what happens on a version conflict.
  • Cost guardrails. Token budgets per person and per session, with usage on the dashboard.
  • Retention. How long messages, versions and audit records are kept, and how a person's data is deleted.
  • Retrieval quality. A set of real questions with known good sources, re-run whenever the index or prompts change.
  • Initial load. Bulk import of the existing wiki spaces before webhooks take over.

Why Postgres with pgvector rather than a separate vector store: the page, its chunks, its vectors and its permissions change in one transaction. That is what makes the sync consistent instead of eventual.
